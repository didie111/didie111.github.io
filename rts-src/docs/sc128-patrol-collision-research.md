# SC1.28: 일꾼 비비기와 P 패트롤의 충돌 차이 조사

조사: 2026-10-03 KST. 프로젝트 기준 커밋 `ce7e4913e8c11475257978fdb81843371e3509a0`, 게임 코드 `25c68e597910ea040f2eca2ee3d7399e6e11de3e`, 버전 `2026.10.03-sc1.28`.

사용자 요청은 일꾼과 다른 병력을 비빈 뒤 P로 땅이나 유닛 주변을 지정해도 원작처럼 섞이고 뭉치지 않는 이유를 조사하는 것이다. **충돌 복구가 없는 것이 아니라, 채취 예외·일반 접근 회피·Patrol의 완료 조건이 공개 재현 엔진과 다르다.** 이번 작업은 조사와 실제 모듈 재현이며 게임 엔진을 변경하지 않았다. 기존 반납·선택 패치는 그대로다.

## 1. 채취 일꾼의 예외를 양쪽 충돌 해제로 단순화했다

OpenBW의 `set_unit_gathering`은 **gathering 상태**와 충돌 복원 명령을 넣는다. 채취 시작만으로 별도 **no_collide 상태**를 켜지 않는다. `unit_can_collide_with(움직이는 쪽, 상대)`는 먼저 상대의 별도 no_collide 등을 확인하고, 그 뒤 움직이는 쪽의 gathering 상태를 검사한다.

동맹 지상 유닛·표시 상태·정상 pathing flag·별도 no_collide 없음으로 조건을 맞추면 다음과 같다. 이 표의 OpenBW 열은 실제 함수를 읽어 조건을 평가한 결과이며 실행 측정이 아니다.

| 검사하는 쪽 → 상대 | OpenBW의 몸체 충돌 대상 | 현재 프로젝트 |
| --- | --- | --- |
| 채취/반납 일꾼 → 일반 마린 | 제외 | 제외 |
| 일반/Patrol 마린 → 채취/반납 일꾼 | 포함 | 제외 |
| 채취 일꾼 → 다른 채취 일꾼 | ReturnGas와 상대 WaitForGas 조건에 따라 다름 | 전부 제외 |
| 일반 마린 → Hold로 전환한 일꾼 | 포함 | 포함 |

우리 `Entity.syncHarvestCollision`은 `gather/ret`를 `noCollide=true`로 묶는다. `groundCollider`, `SH.prepareGround`, `PF.unitsClear/unitObstacles`는 그 일꾼을 검사 목록에서 제거하므로 **Patrol 쪽에서도 일꾼을 보지 못한다.** 채취 명령을 Hold/Stop/Move로 바꾸면 다시 목록에 들어오고 그때에야 이미 겹친 양쪽이 복구한다. 따라서 채취 중부터 일반 병력이 접촉·겹침을 알아보고 반응하는 조건이 재현되지 않는다. 실제 비비기 모양에 미치는 정도는 같은 입력의 OpenBW 실행 비교가 추가로 필요하다.

새 재현에서 SCV/드론/프로브 각각 `gather`와 `ret`일 때 목록 포함=false, Patrol의 4px 보폭 차단=false였다. 같은 좌표에서 Hold로 전환하면 둘 다 true였다. 기존 `collision.test.cjs`는 채취 중 겹친 Hold 병력이 계속 고정되어야 한다고 검사하는 부분이 있다. 이는 현재 양쪽 제외를 보장하는 검사이지, 위 비대칭 조건을 입증하는 원작 동등성 검사가 아니다. 후속 구현에서는 **정상 접근만으로 Hold를 움직이지 않는 조건**과 **이미 실제로 겹친 상태의 복구**를 나눠 검사 기준도 함께 고쳐야 한다.

다만 OpenBW의 `movement_UM_AtRest`는 collision 상태가 있을 때 CheckIllegal로 넘어가며 `check_unit_collision`의 상태 설정도 gathering을 구분한다. 위 충돌 대상 표만으로 “채취 일꾼과 겹친 모든 Hold는 매 틱 즉시 움직여야 한다”고 결론 내리면 안 된다. 충돌 대상, 새로 침범하는 경계 검사, 복구를 깨우는 상태를 각각 비교해야 한다.

## 2. 다음 보폭이 가능한데도 긴 선행 검사에서 크게 우회한다

우리 `steerGround`는 마린 속도 4px에서 `look=max(speed, r+speed*6)=32px`를 먼저 검사하고 22.5° 단위의 방향 후보를 고른다. 짧은 현재 보폭이 비어 있어도 긴 후보가 막히면 먼저 옆으로 꺾을 수 있다. OpenBW의 이동 접촉 검사는 실제 새 몸체 경계를 보고, 접촉 뒤 `FixCollision`에서 상대의 목표·경유점·방향·접촉 카운터에 따라 대기/슬라이드/재탐색 등을 나눈다. Teippi의 실제 이동 충돌 검색도 현재 보폭으로 새로 들어가는 사각 경계를 검사한다. 원작 길찾기에 선행 검사 자체가 없다는 뜻은 아니다.

단일 재현은 Patrol 마린 `(400,400) → (700,400)`, Hold 마린 `(440,400)`이다. 첫 틱에서 다음 4px 직진은 충돌하지 않지만 `steerGround`가 `(4,0)`을 `(3.6955,1.5307)`로 바꾸며 22.5° 우회 후보를 택했다. 실제 이동은 이후 별도 회전 제어도 받으므로 이 수치를 최종 몸체 방향의 순간 변경이라고 부르지 않는다.

이 선행 거리만 실제 보폭으로 줄인 **격리 VM 실험**에서는 처음 3틱의 직진 후보를 유지했다. 하지만 아래 복합 군집의 최종 면적은 오히려 커졌다. 이것만 적용해 해결됐다고 할 수 없다.

## 3. 일반 접촉과 Patrol의 상태 전환이 축약돼 있다

`UM_FixCollision`은 단순히 움직임 여부만 보는 것이 아니라 상대의 실제 도착점·경유점·진행 방향·접촉 상태를 사용한다. `UM_WaitFree`는 충돌을 다시 검사하면서 25회 이후 난수에 따라 `ForceMoveFree` 또는 `RepathMovers`로 나뉜다. `SlideFree`는 1px씩 시험 이동한다. `ForceMoveFree`는 속도/경로를 정리해 다시 출발하는 분기이며, 모든 병력이 충돌 없이 뭉치는 전역 유령 이동이 아니다.

우리 정상 접촉은 같은 쪽으로 움직이는 상대에 대해서만 25회 대기한 뒤 항상 120틱의 이동 몸체 재탐색 구간을 켠다. 그 외에는 주로 각도 후보로 우회한다. `recoverGround`에 CheckIllegal/MoveToLegal 성격의 대기·실제 짧은 이동·재검사는 이미 있으며, 이것이 없어서 비비기가 전부 실패한다고 해석하면 안 된다. **일반 접촉의 대응이 복구 바깥에서 단순화된 것**이 남은 차이다.

OpenBW `order_Patrol`은 왕복 명령 큐, 판정 타이머 15, 실제 이동 목표 도달, immovable 여부와 실제 종료 위치를 함께 사용한다. 우리 `Entity.orderLogic`은 `moveGroup`이 완료를 반환한 틱에 원래 두 끝점을 즉시 교환한다. 실제 목표 점유를 검사하는 `PF.goalBlocker`에는 이미 Patrol이 포함돼 있으므로 “Patrol은 공유 목표 검사가 없다”는 설명은 틀리다. 차이는 목표 점유 이후의 완료 상태·왕복 큐 처리까지 일반 이동 완료로 묶은 데 있다.

현재 `UI.execMode`의 P는 땅이든 유닛 위든 클릭 좌표의 Patrol을 만든다. OpenBW `attack_move_movement`도 Patrol의 이동 목표에는 좌표를 사용한다. **유닛을 P로 눌렀다는 이유만으로 충돌을 해제하거나 계속 겹쳐야 하는 별도 규칙을 확인한 것은 아니다.** 원작에 맞는 뭉침은 채취 상태·기존 겹침·목표 점유·접촉 상태의 조합으로 검증해야 한다.

## 실제 모듈 재현과 거리 축소 실험의 한계

실행: `node rts-src/scripts/patrol-collision-repro.cjs`.
[실행 스크립트](../scripts/patrol-collision-repro.cjs)와 [원시 결과](sc128-patrol-collision-results.json)를 함께 보관한다. 외부 패키지는 필요 없다. 기본 게임 코드와 `look=speed` 실험을 각각 새 VM에서 실행하며 소스 파일을 수정하지 않는다. SCV/드론/프로브 3종 모두 같은 결과를 냈다. 현재 세 일꾼의 이동 프로필이 같다는 점도 함께 고려한다.

마린 12기와 일꾼 11기는 기존 가스 드릴 검사와 같은 좌표다. 일꾼을 미정제 가스에 접근시키고 첫 일꾼/마린 겹침인 32틱에서 일꾼을 Hold로 전환한다. 병력은 Hold를 유지하거나 P `(550,590)`을 지정한다. 이 시점부터 240틱(시뮬레이션 10초)을 측정했다. 폭/높이는 **유닛 중심의 경계**이고 원작 스프라이트 면적이 아니다.

DAT 사각형은 양 끝 경계에 +1을 포함한다. 현재 원형 거리는 `.85*(r1+r2)`이며 대부분 이미 원작 사각 몸체 폭보다 작다. 단순히 “반지름이 커서 못 뭉친다”는 진단은 이 자료와 맞지 않는다. 사각 몸체/실수 좌표/절차적 스프라이트가 원작과 달라 보이는 정도도 별개다. 그림이 겹치는 것과 실제 충돌 몸체가 불법으로 겹치는 것은 구분해야 한다.

## 후속 구현의 구체적인 순서

1. gathering과 별도 no_collide를 분리하고 **움직이는 쪽과 상대를 받는 충돌 조건**을 도입한다. 지상 목록·국소 경로·순차 이동·실제 겹침 복구가 모두 같은 조건을 사용해야 한다. 채취 일꾼의 통과는 보존하면서 일반 병력이 그 일꾼을 볼 수 있어야 한다.
2. 정상 보폭이 가능한 경우와 실제 접촉한 경우를 분리한다. 접촉 상대의 목표/방향에 따른 대기·짧은 슬라이드·재출발·재탐색을 원본 분기로 맞춘다. 기존 불법 겹침 복구와 고정 몸체 보호를 유지한다.
3. Patrol 왕복 큐와 실제 완료 위치·점유 상태를 구분한다. 같은 땅 지정/유닛 위치 지정/채취 유지/Stop·Hold 전환을 따로 재현하고 원작 실행과 비교한다.
4. 기존 채취·반납·공격·고정 상태 회귀 전체와 대량 유닛 성능을 확인한다. 비비기를 늘리려는 고정 시간·전체 감속·무조건 충돌 해제는 적용하지 않는다.
